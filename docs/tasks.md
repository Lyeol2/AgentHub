# GitFlow 작업

프로젝트의 **작업** 탭은 요구사항, Git 브랜치, 전용 작업 폴더, AI 세션, Pull Request를 하나의 작업으로 연결한다. 일반적인 세션은 기존 방식으로 만들 수 있다.

## 작업 시작

**새 작업**에 원하는 일을 적으면 일회성 AI가 제목, 작업 내용, 완료 기준을 초안으로 정리한다. 같은 대화에서 추가 요청을 보내거나 초안을 직접 수정할 수 있다. 초안 작성에 사용할 AI와 모델을 선택할 수 있으며, 기존 CLI 설치와 인증을 그대로 사용한다. **직접 입력**으로 제목과 내용을 작성해도 된다.

새 작업 창은 지난번에 만든 작업의 유형(배포 준비는 제외), 담당 AI, 모델, 권한을 기억해 채운다. **작업할 폴더**(워크트리 만들기 / 워크트리 만들지 않기)는 세부 설정을 펼치지 않아도 보이며, 바로 아래에 어느 폴더에서 일하게 되는지 경로를 보여 준다. 원본 폴더에서 작업하면 원본 폴더의 브랜치가 바뀌므로 이 선택은 기억하지 않고 매번 워크트리 만들기로 시작한다. 제목과 내용은 비운다. 담당 AI는 이 PC에서 찾은 CLI 중에서만 고를 수 있으며, 찾은 CLI가 없으면 작업을 만들지 않고 설정에서 설치하거나 경로를 지정하라고 안내한다.

초안 작성 중에는 작업·브랜치·폴더·세션을 만들지 않는다. 내용을 확인하고 **만들고 시작**을 누르면 작업마다 충돌하지 않는 이름으로 브랜치와 `<프로젝트>.agenthub/` 아래의 작업 폴더를 만들고, 선택한 담당 AI 세션에 제목·작업 내용·완료 기준을 첫 요청으로 보낸다. 모델·권한·브랜치·폴더 같은 세부 설정은 **고급 설정**에서 조정한다. 시작 요청의 응답이 끊기거나 세션 생성에 실패하면 이미 만든 작업을 보존하고 오류를 표시하며, 같은 생성 요청을 다시 보내거나 앱을 다시 열어도 첫 요청을 자동으로 반복하지 않는다. 작업과 세션 기록을 확인한 뒤 이어서 진행한다.

새로 만들 때 **브랜치 이름**과 **작업 폴더 이름**을 직접 정할 수 있다. 브랜치 이름은 유형 접두어(`feature/` 등) 뒤에 붙고, 작업 폴더는 `<프로젝트>.agenthub/` 아래에 그 이름으로 만든다. 비우면 `<작업ID>-<제목>`과 `task-<작업ID>`를 자동으로 쓴다. `feature/login`처럼 접두어까지 적으면 접두어를 한 번만 붙인다. 다른 유형의 접두어(기능 작업에 `hotfix/…`)로 시작하면 기준·대상 브랜치가 어긋나므로 만들지 않는다. 같은 이름의 브랜치나 폴더가 이미 있으면 만들지 않는다.

작업 브랜치에서 **새로 만들기** 또는 **기존 브랜치 선택**을 고른다. 기존 브랜치를 선택하면 체크아웃된 작업 폴더와 미커밋 변경을 그대로 이어 사용한다. 새로 만들 때 **워크트리 만들지 않기**을 고르면 전용 폴더 대신 프로젝트 원본 폴더를 새 작업 브랜치로 전환해 그 자리에서 작업한다. 원본 폴더에 커밋하지 않은 변경이나 실행 중인 세션이 있으면 시작하지 않으며, 원본 폴더를 쓰는 작업은 프로젝트마다 하나만 둘 수 있다. 기존 브랜치 선택과는 함께 쓸 수 없다. 아직 작업 폴더가 없는 로컬 브랜치는 전용 폴더에 연다. 이미 작업에 연결된 브랜치는 해당 작업에서 세션을 추가하며, 같은 브랜치로 작업을 중복 생성하지 않는다.

**GitFlow 설정**에서 프로젝트의 배포·개발 브랜치 이름과 기능 개발·긴급 수정·배포 준비 브랜치의 접두어를 직접 입력할 수 있다. 예를 들어 개발 브랜치를 `develop` 대신 `Develop`로 저장하면 새 기능 작업의 기준과 PR 대상에 `Develop`를 사용한다. 대소문자를 그대로 보존하며, 접두어는 `feature/`나 `Feature/`처럼 설정한다.

설정은 프로젝트별로 저장되고 앱을 다시 열어도 유지된다. 설정을 바꿔도 기존 Git 브랜치 이름은 바뀌지 않으며, 이미 만든 작업은 생성할 때의 브랜치 설정을 계속 사용한다. 다음 표는 설정을 바꾸지 않았을 때의 기본값이다.

| 유형 | 기준 | 브랜치 | PR 대상 |
| --- | --- | --- | --- |
| 기능 개발·일반 수정 | 원격 develop | `feature/*` | develop |
| 긴급 수정 | 원격 main | `hotfix/*` | main |
| 배포 준비 | 원격 develop | `release/*` | main |

배포 준비는 버전(예: `1.2.0`, `v1.2.0-rc.1`)을 받아 `release/<버전>` 브랜치를 만들고, 기존 `release/*` 브랜치를 고르면 접두어 뒤 이름을 버전으로 쓴다. 버전은 작업 카드와 PR 설명에 표시한다. 버전 올리기·태그는 프로젝트의 배포 절차에 맡긴다.

시작할 때 원격 main과 기준 브랜치를 다시 확인한다. develop이 없는 저장소의 초기 개발 기준은 최신 main이다. develop을 원격에 게시할 때는 기존 브랜치를 덮어쓰지 않는다. main의 변경이 develop에 누락된 경우에는 개발 통합을 먼저 마친다.

## 최신 확인과 동기화

최신 확인은 원격 커밋을 읽고 작업 기준과 비교한다. 확인한 시간과 결과를 표시하며, 연결이나 인증에 실패하면 최신으로 표시하지 않는다. 최신 확인 자체가 작업 파일을 병합하지는 않는다.

작업 브랜치에 대상 브랜치의 변경을 반영할 때는 **동기화**를 사용한다. 실행 중인 세션이나 커밋하지 않은 변경이 있으면 먼저 작업을 멈추거나 커밋한다. 원본 폴더에서 하는 작업이 아니면 원본 프로젝트 폴더는 전환하지 않는다.

## 작업 카드의 진행 단계

작업 카드는 GitFlow 진행을 한 줄의 노선으로 보여 준다.

`기준 브랜치 ─분기→ 브랜치 만들기 → 작업 폴더 → 작업 → 커밋 → Pull Request(또는 대상 반영) ─병합→ 대상 브랜치`

- 끝난 단계는 초록 체크, 지금 단계는 파란 테두리, 남은 단계는 점선으로 표시한다. 긴급 수정·배포 준비는 대상(main) 뒤에 `─역반영→ develop` 단계가 더 붙는다.
- 카드 위쪽 폴더 줄에 작업 폴더의 종류(워크트리·원본 폴더·기존 작업 폴더)와 전체 경로를 보여 준다. 폴더가 사라졌으면 `폴더 없음`, 정리한 뒤에도 잠긴 파일 때문에 폴더가 남았으면 `정리 후 폴더가 남음`을 표시한다.
- 노드에는 브랜치 이름, 작업 폴더(`.agenthub/<이름>` 또는 원본 폴더), 세션 수와 실행 여부, 커밋 수와 짧은 해시(커밋 전이면 `변경 N개 · 커밋 전`), PR 번호와 상태를 적는다. 원격 기준 브랜치에 새 변경이 있으면 기준 노드를 경고 색으로 바꾼다.
- 카드를 보거나 작업을 진행할 때마다 `GET /api/tasks/:id/status`로 로컬 Git 상태(커밋 안 된 변경 수, 앞선 커밋 수, 푸시 여부)를 읽어 단계를 다시 그린다. 이 조회는 네트워크를 쓰지 않고 작업 기록도 바꾸지 않는다.
- 카드 아래에는 지금 단계에서 할 수 있는 동작만 둔다. 진행 중이면 **세션 열기 · 변경 보기 · 마무리**, 검토 대기면 **PR 열기 · 세션 열기 · 병합 검토**, 완료면 **PR 보기 · 작업 폴더 정리**다. 기준 브랜치가 앞서 있으면 마무리 대신 **기준 반영**을 먼저 보여 준다.
- 할 수 없는 동작은 꺼 두고 바로 아래에 이유를 적는다. 예: 세션이 작업 중, 아직 변경이 없음, 커밋하지 않은 변경이 있음, 이전 요청의 결과를 모름(최신 상태 확인 필요), develop 역반영 전이라 정리 불가.
- 세션 추가, 최신 상태 확인, 대상 브랜치 푸시, 이슈 연결, 작업 삭제는 카드의 `⋯` 메뉴에 있다.
- 목록 위의 기준 정보 줄은 `기준 브랜치 develop · 배포 브랜치 main · origin과 같음 · 방금 확인`처럼 GitFlow 설정과 원격 확인 결과를 보여 준다.

## 되돌리기 어려운 동작의 확인

작업 폴더 정리, 작업 삭제, 실행 중인 세션을 멈추거나 커밋하지 않은 변경을 버리는 강제 삭제, PR 병합, 로컬 대상 브랜치 반영, 대상 브랜치 푸시, develop 역반영은 실행 전에 확인 창을 띄운다. 확인 창은 **바뀌는 것**, **그대로 남는 것**, **주의**를 나눠 보여 주고, 작업 삭제에서는 로컬 브랜치를 함께 지울지 같은 창에서 고른다. 취소하거나 Esc로 닫으면 아무 요청도 보내지 않는다.

## git 오류 안내

자주 나는 git 오류는 원문 대신 한국어 설명과 해결 방법으로 보여 준다. 원문은 **Git 원문 보기**를 펼쳐 확인할 수 있다.

| reason | 언제 | 해결 방법 |
| --- | --- | --- |
| `git-conflict` · `task-conflict` | 병합·받기·기준 반영 중 같은 부분이 양쪽에서 바뀜 | 실행 전 상태로 되돌리고 충돌 파일 목록을 보여 준다. 카드의 **세션에 충돌 해결 요청**으로 작업 세션에 병합과 충돌 해결을 맡기거나 직접 고친 뒤 다시 반영 |
| `task-git-operation` · `task-recovery-required` | 시간 초과·강제 종료로 병합·리베이스가 작업 폴더에서 중간에 멈춤 | 카드의 **진행 중인 Git 작업 취소**로 Git이 시작 전 커밋으로 되돌린다. 잠금 파일(`index.lock`)은 지우지 않는다 |
| `git-push-rejected` | 원격 브랜치에 아직 받지 않은 커밋이 있음 | 최신 확인(Fetch) 후 Pull·기준 반영, 다시 푸시 |
| `git-push-protected` | 원격의 보호 규칙이 직접 푸시를 거절 | 작업 브랜치에서 Pull Request로 반영 |
| `git-dirty` | 커밋하지 않은 변경이 덮어써질 수 있음 | 먼저 커밋하거나 정리 |
| `git-diverged` | 로컬과 원격이 갈라져 앞으로 감기 불가 | Merge 또는 Rebase로 합치기 |
| `git-no-upstream` | 추적할 원격 브랜치가 없음 | Push로 게시하면서 추적 설정 |
| `git-locked` | 다른 Git 작업이 저장소를 쓰는 중(`index.lock`) | 끝난 뒤 다시 시도. 잠금 파일은 지우지 않음 |
| `git-network` | 원격에 연결하지 못함 | 인터넷 연결과 원격 주소 확인 |
| `git-auth` · `git-auth-ssh` | HTTPS·SSH 인증 실패 | GitHub 로그인 버튼 또는 SSH 키 등록 |

인증 실패는 푸시 거부 문구와 함께 나와도 인증을 먼저 안내한다. 작업 카드에 남는 오류에는 해결 방법(`errorHint`)도 함께 저장한다.

## 변경 검토와 반영

작업 카드의 **변경 보기**·**마무리**는 한 화면에서 `변경 커밋 → 기준 반영 → PR 만들기(또는 대상 브랜치 반영)` 단계를 차례로 안내한다. 완료한 단계에는 표시가 붙고 지금 할 단계는 파란 테두리로 강조하며, 버튼은 지금 해야 할 다음 행동 하나만 보여준다.

1. **변경 커밋**: 커밋하지 않은 파일 목록과 파일별 diff를 보고 커밋할 파일을 고른다. 고르지 않은 파일은 그대로 남으며, 남은 변경이 있으면 다음 단계로 넘어가지 않는다. 이미 커밋을 마쳤다면 커밋 메시지를 묻지 않는다. 확인한 뒤 파일이나 HEAD가 바뀌면 목록을 다시 확인해야 한다.
2. **기준 반영**: 대상 브랜치가 앞서 있으면 그 변경을 작업 브랜치에 먼저 반영한다. 반영한 뒤에는 검증 결과를 다시 확인한다.
3. **반영**: 현재 커밋과 검증 결과를 확인했다고 표시한 뒤 반영 방식에 따라 진행한다.

| 반영 방식 | 진행 순서 |
|---|---|
| 게시하고 PR 만들기 | 브랜치 게시 → 유형에 맞는 대상으로 PR 생성 → 리뷰 대기. PR을 만든 뒤에는 카드의 **병합 검토**에서 병합 방식(병합 커밋·하나로 합치기·순서대로)을 골라 병합한다. |
| 로컬 대상 브랜치에 반영 | 대상 브랜치에 로컬 병합 → 반영 완료. 필요하면 원격 푸시를 함께 선택하거나 나중에 카드의 **대상 브랜치 푸시**로 보낸다. |

로컬 반영에서 대상 브랜치가 어느 폴더에도 체크아웃되어 있지 않으면 병합에 쓸 임시 작업 폴더를 만들고, 병합이 끝나면 지운다. 그래서 대상 브랜치가 임시 폴더에 묶여 원본 폴더에서 `git switch develop`이 막히는 일이 없다. 대상 브랜치 푸시는 작업 폴더 없이 커밋만 보낸다.

새 작업의 기본 반영 방식은 **GitFlow 브랜치 설정**에서 프로젝트별로 정한다. 작업마다 검토 화면에서 바꿀 수 있지만, 이미 PR이 있는 작업은 PR 방식으로 고정한다. 이미 PR이 연결된 작업은 기존 PR을 사용한다. GitHub CLI 설치와 인증은 설정 화면의 기존 기능을 사용한다.

부분 실패해도 처음부터 다시 하지 않는다. 예를 들어 푸시는 성공하고 PR 생성만 실패했다면 다시 열었을 때 남은 단계부터 이어간다. 원격 작업의 응답이 끊겨 완료 여부를 알 수 없으면 먼저 **최신 확인**으로 결과를 조회한다. 원격 쓰기를 자동 반복하지 않는다.

상태는 **진행 중 → 검토 대기(PR 생성) → 완료(병합) → 정리됨**으로 바뀐다. GitHub에서 직접 병합해도 작업 탭을 열 때와 탭을 열어 둔 동안 몇 분마다 검토 대기 작업의 PR 상태를 확인해 완료로 바꾸고, 카드에 **작업 폴더 정리**를 안내한다. 정리는 확인 창을 거쳐야 실행된다. **최신 확인**을 누르면 바로 확인한다. PR 검토·병합은 Git 탭의 Pull Requests 화면에서도 진행할 수 있다.

### 배포 준비·긴급 수정의 develop 반영

배포 준비와 긴급 수정은 main에 반영한 뒤 develop에도 반영해야 끝난다. develop에 반영하기 전에는 카드에 안내가 남고 작업 폴더를 정리할 수 없다.

| 반영 방식 | develop 반영 |
|---|---|
| 로컬 대상 브랜치에 반영 | main에 병합한 뒤 이어서 작업 브랜치를 로컬 develop에 병합한다(로컬 develop이 없으면 원격 develop, 그것도 없으면 방금 반영한 main에서 만든다). 충돌하면 develop 병합만 취소해 실행 전 상태로 되돌리고 main 반영은 유지한다. Git 탭에서 직접 병합해 충돌을 해결하고 **최신 확인**을 누르거나, 카드의 **develop에 반영**으로 다시 시도한다. **대상 브랜치 푸시**는 main과 develop을 함께 보낸다. |
| 게시하고 PR 만들기 | PR이 main에 병합되면 카드의 **develop 반영 PR 만들기**로 `main → develop` PR을 연다. 같은 PR이 이미 열려 있으면 그 PR을 연결하고, 원격 develop이 없으면 최신 main에서 만든다. 반영 PR이 병합되면 최신 확인으로 반영을 확인한다. |

GitFlow처럼 main과 develop에 따로 병합해 병합 커밋이 달라도, main의 내용이 develop에 모두 들어 있으면 반영된 것으로 본다.

## GitHub 이슈 연결

작업 카드의 **더 보기 → 이슈 연결**에서 GitHub 이슈를 작업에 연결한다. **기존 이슈 번호로 연결**하거나 **이 작업 내용으로 새 이슈 만들기**를 고른다. 새 이슈는 제목·작업 내용·완료 기준으로 만들고, 내 GitHub 계정에 지정하며 `agenthub` 라벨을 붙인다(팀 작업과 같은 방식). 같은 이슈는 정리하지 않은 작업 하나에만 연결한다.

- 연결은 작업 기록에 저장되어 앱을 다시 열어도 유지된다. 기록만 바꾸므로 AI 세션이 실행 중이어도 연결할 수 있다.
- 카드에 `이슈 #번호 · 열림/닫힘`과 제목을 보여 주고, 누르면 GitHub 이슈가 열린다. **최신 확인**을 할 때 이슈 상태도 다시 읽는다. 이슈를 읽지 못해도 작업 최신 확인은 실패로 만들지 않고, 카드에 사유를 보여 준다.
- 작업으로 PR을 만들면 PR 설명에 `Closes #번호`를 넣는다. GitHub는 PR이 저장소 기본 브랜치에 병합될 때만 이슈를 자동으로 닫으므로, develop으로 가는 기능 작업은 이슈를 직접 닫는다.
- **이슈 연결 해제**는 작업 기록에서만 지우고 GitHub 이슈와 PR은 그대로 둔다.
- 새 이슈 생성 응답이 끊겨 결과를 알 수 없으면 다시 만들지 않는다. GitHub에서 생성 여부를 확인한 뒤 번호로 연결한다.
- 팀 작업 탭에서 받은 작업을 시작한 세션도 그 이슈와 연결되며, 세션을 다시 만들면 새 세션이 연결을 이어 받는다.

## GitHub 연결 오류

GitHub CLI가 없거나 로그인하지 않았거나 권한이 부족하면 작업 탭·변경 검토·이슈 연결 화면에 원인과 해결 방법을 보여 주고, 설정의 **GitHub CLI 설치·로그인** 버튼을 함께 띄운다. 오류는 작업 기록에 사유와 함께 남아 다시 열어도 같은 안내가 보인다. 자세한 사유 목록은 [git-client.md](git-client.md)의 현재 구현을 따른다.

## 흐름의 작업 노드

흐름 탭에서 **새 작업**과 **작업 마무리**를 노드로 둘 수 있다. 예를 들어 `버튼 → 새 작업 → 구현 세션 → 작업 마무리 → 보고 세션`으로 이으면 버튼 한 번으로 작업 브랜치를 만들고, 세션이 구현을 마치면 승인 후 PR까지 만든다.

- **새 작업**은 작업 유형·제목 템플릿·배포 버전·워크트리 만들지 않기를 설정한다. 제목과 버전에는 앞 노드의 결과 `{{input}}`와 입력 폼 값 `{{key}}`를 쓸 수 있고, 결과의 첫 줄을 제목으로 쓴다. 작업 탭의 새 작업과 같은 검사를 거쳐 브랜치·작업 폴더·작업 기록을 만들지만 세션은 만들지 않는다.
- 새 작업의 성공 출력에 연결한 세션은 **Git 작업 폴더 사용**(기본으로 켜짐)에 따라 작업 폴더로 옮겨 작업에 연결된다. 대화 기록이 없는 세션만 옮기며, 이미 다른 작업에 연결된 세션은 옮기지 않는다. 명령 노드는 실행 폴더를 **이전 노드의 작업 폴더**로 두면 작업 폴더에서 실행된다.
- 같은 실행에서 새 작업 노드가 다시 불리면(반복 제어 등) 앞서 만든 작업을 다시 쓴다. 새로 실행해도 지난번에 만든 작업이 병합·정리 전이면 그 작업과 작업 폴더를 이어 쓰고, 병합·정리했거나 지운 뒤에만 새 작업을 만든다.
- **작업 마무리**는 반영 방식과 커밋 메시지·PR 설명·검증 결과 템플릿을 설정한다. 반영 방식은 **작업 설정 따르기**(기본), **게시하고 PR 만들기**, **로컬 대상 브랜치에 반영** 중에서 고르며, 로컬 반영은 대상 브랜치 원격 푸시를 함께 선택할 수 있다. 노드 카드에 진행 순서가 표시된다. 커밋 메시지를 비우면 `feat: 작업 제목`(긴급 수정은 `fix:`, 배포 준비는 `chore:`)을 쓴다. 마무리할 작업은 앞 세션이 속한 작업, 없으면 이번 실행에서 새 작업 노드가 만든 작업이다.
- 작업 마무리로 들어가는 연결은 기본으로 승인을 받는다. 원격 응답이 끊겨 결과를 알 수 없으면 실패로 넘기고 다시 시도하지 않으므로, 작업 탭에서 **상태 확인**을 먼저 한다.
- 두 노드 모두 성공·실패·항상·수동 조건만 쓴다. 중지하면 이미 시작한 Git 작업은 끝까지 진행하고 결과만 다음 노드로 넘기지 않는다.

## 세션과 정리

세션을 종료·삭제해도 작업의 브랜치와 폴더, PR은 유지한다. 작업에서 새 세션을 만들면 같은 작업 폴더를 이어 사용한다. 동일 작업 폴더에서 동시에 두 세션을 실행하지 않는다.

일반 **새 세션**에서도 작업 폴더 분리를 선택한 뒤 기존 작업 브랜치를 고를 수 있다. 작업 생성과 같은 브랜치 목록을 사용하며, 작업이 소유한 브랜치를 고르면 그 작업에 세션이 연결된다. 프로젝트 원본의 main·develop, 잠긴 폴더, 사라진 작업 폴더는 선택할 수 없다. 채팅은 작업 브랜치를 사용하지 않는다.

병합한 작업은 **정리**로 작업 폴더와 로컬 브랜치를 제거한다. 실행 중인 세션, 미커밋·미추적 파일, 게시되지 않은 커밋, 병합 후 추가 커밋이 있으면 정리를 중단하고 남은 커밋 목록을 보여 준다. 병합한 뒤 **기준 반영**으로 생긴 병합 커밋이나 하나로 합치기(squash) 병합처럼 내용이 이미 대상 브랜치에 모두 들어 있으면 추가 커밋으로 보지 않는다. 작업 폴더가 이미 사라졌으면 남은 Git 기록과 로컬 브랜치만 정리한다.

Windows에서 편집기·탐색기·백신·남은 개발 서버가 파일을 잡고 있으면 잠시 기다리며 다시 지운다. `node_modules`처럼 큰 폴더도 끝까지 지운다. 그래도 Git 기록이 남으면 정리를 멈추고 폴더를 연 프로그램을 닫으라고 안내한다. Git 기록은 지웠는데 폴더 일부만 남았으면 정리는 끝내고 카드의 **남은 폴더 다시 지우기**로 다시 지울 수 있다. 세션 삭제·작업 삭제·프로젝트 제거·Git 탭의 폴더 정리도 같은 방식으로 지운다. 원격 브랜치와 PR은 보존한다. 원본 폴더에서 한 작업은 작업 폴더를 지우지 않고, 원본 폴더를 작업 전 브랜치(없으면 PR 대상 브랜치)로 되돌린 뒤 작업 브랜치를 지운다. 대화 기록과 작업 기록은 남고, 정리한 작업의 세션은 원본 폴더로 옮겨 실행되지 않는다.

기존 브랜치를 골라 시작한 작업의 브랜치는 정리 후에도 보존한다. 기존 작업 폴더를 함께 사용했다면 그 폴더도 보존하며, 이번 작업에서 새로 연 폴더만 제거한다. 공유 폴더는 세션 삭제나 프로젝트 제거로 지우지 않는다.

원본 폴더에서 한 작업을 지우면 로컬 브랜치를 남기더라도 원본 폴더는 작업 전 브랜치로 되돌린다. `.git` 파일이 지워지는 등 손상된 작업 폴더는 변경 여부를 확인할 수 없으므로 강제 삭제를 확인한 뒤 지운다.

더 이상 필요 없는 작업은 작업 카드의 **작업 삭제**로 지운다. 연결된 세션을 멈추고 삭제하며, 그 세션을 열어 둔 화면이나 팝업 창은 자동으로 닫힌다. AgentHub가 만든 작업 폴더를 지우고 작업 카드도 목록에서 사라진다. 로컬 브랜치는 삭제 확인 창에서 함께 지울지 고른다. 실행 중인 세션이나 커밋하지 않은 변경이 있으면 무엇을 멈추거나 버리는지 보여 주는 확인 창을 한 번 더 띄운다. 원본 폴더에서 한 작업과 기존 작업 폴더를 고른 작업은 폴더를 지우지 않으며, 원격 브랜치와 PR은 항상 남긴다.

작업 정보는 AgentHub 데이터 폴더에 저장되며 앱을 다시 열어도 유지된다. 기존 `agenthub/*` 브랜치와 세션을 자동으로 작업으로 전환하지 않는다. 앱 자체의 버전 증가·태그·배포 스크립트는 이 작업 흐름과 별개다.

작업 폴더 생성이 중간에 실패해 브랜치가 남은 경우에도 작업 기록을 보관한다. 오류를 확인한 뒤 해당 작업의 **새 세션**을 누르면 기존 브랜치를 유지하면서 폴더 준비를 이어간다. 세션을 모두 삭제한 작업도 저장된 AI·모델·권한·역할로 다시 연결할 수 있다.
