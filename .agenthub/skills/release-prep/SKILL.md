# 릴리스 준비

AgentHub 릴리스(`npm run release`)를 돌려도 되는지 점검한다. **릴리스 자체는 직접 실행하지 않는다.** 실제 릴리스는 흐름의 명령 노드가 사람의 승인을 받은 뒤 실행한다.

릴리스는 **마지막 커밋(HEAD)** 기준이다. `npm run release`는 HEAD를 임시 작업 트리에 꺼내 테스트·빌드하므로 커밋하지 않은 변경은 릴리스에 들어가지 않고 작업 트리에 그대로 남는다. 그러니 점검도 작업 트리가 아니라 HEAD를 본다.

이 스킬은 점검이 중심이다. 코드는 고치지 않는다. 하나라도 걸리면 바로 실패로 끝낸다.
예외는 둘이다.
- README처럼 기능을 설명하는 문서가 바뀐 기능과 어긋나면 문서를 고쳐 `docs:` 커밋으로 남긴다(4단계). 릴리스는 HEAD 기준이라 커밋해야 릴리스에 들어간다.
- 점검을 모두 통과하면 사용자용 업데이트 내역 초안 `release-notes.draft.md`를 쓴다. 이 파일은 git 제외 파일이라 커밋에 섞이지 않는다.

## 순서
1. `git status --porcelain`으로 커밋하지 않은 변경을 본다. 있어도 실패가 아니다. 릴리스에 들어가지 않는 파일로 목록만 알린다.
   - 단, `package.json`이나 `package-lock.json`이 바뀌어 있으면 버전 커밋과 겹쳐 릴리스가 시작되지 않으므로 **실패**다.
2. `git log --oneline`으로 지난 릴리스(`chore: release vX.Y.Z`) 이후 커밋을 파악한다. 커밋이 없으면 릴리스할 것이 없으므로 **실패**다.
3. 테스트는 릴리스가 HEAD로 다시 돌리므로 여기서는 HEAD 기준 결과를 확인한다. 커밋하지 않은 변경이 없으면 `npm test`를 그대로 돌리고, 있으면 `git worktree add --detach <임시 경로> HEAD`로 꺼내 그 안에서 `npm ci`·`npm test`를 돌린 뒤 `git worktree remove --force <임시 경로>`로 지운다. 실패하면 고치지 않고 실패한 테스트와 출력을 보고하고 **실패**로 끝낸다.
4. README처럼 기능을 설명하는 문서가 지난 릴리스 이후 바뀐 기능과 어긋나는지 HEAD 기준(`git show HEAD:README.md`, `git diff <지난 릴리스>..HEAD`)으로 본다. 바뀐 기능만이 아니라, 없어지거나 동작이 바뀐 기능을 아직 설명하는 문장(예: 없어진 옵션, 더는 일어나지 않는 흐름, 더는 맞지 않는 알려진 한계)도 찾는다.
   - 어긋나면 지금 코드(HEAD)의 동작에 맞게 문서를 고친다. 코드를 읽어 실제 동작을 확인하고 쓰며, 코드에 없는 기능을 지어내지 않는다. 주변 문장의 말투와 형식을 따른다.
   - 고칠 문서 파일에 이미 커밋하지 않은 변경이 있으면 다른 세션이나 사람이 손대던 것이다. 그 변경이 바로 이 어긋남을 고친 것이면 그 파일만 담아 커밋한다. 아니면 그 변경은 건드리지도 커밋에 담지도 않고, **내가 고친 줄만** 커밋한다.
     - HEAD 판을 꺼내 고친다: `git show HEAD:<경로> > <임시 파일>`로 꺼내 그 임시 파일에 수정을 적용한다.
     - 그 임시 파일을 인덱스에만 올린다: `git hash-object -w <임시 파일>`로 얻은 해시로 `git update-index --cacheinfo 100644,<해시>,<경로>`. 인덱스에 다른 파일이 올라가 있지 않은지 `git diff --cached --name-only`로 먼저 확인한다.
     - 작업 트리 파일에도 같은 수정을 적용해, 커밋한 뒤에도 작업 트리에 내 수정이 되돌려진 것처럼 보이지 않게 한다. 다른 세션의 변경은 그대로 남는다.
     - `git diff --cached <경로>`에는 내 수정만, `git diff <경로>`에는 다른 세션의 변경만 보이는지 확인한 뒤 커밋한다.
     - 내가 고칠 줄이 다른 세션이 고치는 중인 줄과 겹치면, 어느 쪽이 맞는지 정할 수 없으므로 고치지 말고 보고하고 **실패**로 끝낸다.
   - 고친 문서 파일만 담아(커밋하지 않은 변경이 없는 파일은 `git add <경로>`, 있는 파일은 위 방법) `docs: <무엇을 맞췄는지 한국어 요약>` 형식으로 커밋한다(본문에 고친 곳을 `- ` 목록으로). 사용자 요청에 따라 Claude 등 AI의 `Co-Authored-By` 서명이나 생성 도구 표기는 추가하지 않는다. 다른 커밋하지 않은 변경은 담지 않는다.
   - 문서만 고친 커밋이므로 3단계 테스트는 다시 돌리지 않는다. 커밋 후 HEAD가 바뀌므로 이후 단계(특히 7단계의 base)는 새 HEAD로 한다.
   - 코드가 문서와 다르게 잘못 동작하는 것으로 보이면(문서가 맞고 코드가 틀림) 문서를 고치지 말고 보고하고 **실패**로 끝낸다.
5. 지난 릴리스 이후 HEAD에 포함된 변경으로 버전 단위를 자동 선택한다. 따로 선택을 묻지 않는다.
   - 사용자가 버전이나 단위를 정해 주었으면(예: "0.2.0으로") 그것을 따른다. 지금 버전에서 patch·minor·major 중 하나로 그 버전이 되면 그 단위를 `bump`에 적고, 어느 단위로도 되지 않으면(예: 0.1.17 → 0.3.0) 릴리스 명령을 `npm run release -- <버전>`으로 바꿔야 한다고 알린다.
   - 큰 기능 추가나 주요 사용 흐름이 달라지는 변경은 minor로 올린다. 예를 들어 `0.1.17`에서 `0.2.0`으로 올린다.
   - 기존 사용자와의 호환이 깨지는 변경은 major, 그 외 버그 수정·작은 개선·문서·내부 정리는 patch로 한다. 파일 수나 수정 줄 수만 많다는 이유로 minor로 올리지 않는다.
   - 고른 단위는 7단계 초안의 `bump`에 기록한다. `npm run release`가 이를 읽어 자동으로 버전을 올리므로 명령 노드를 수동으로 바꾸라고 안내하지 않는다. 명령에 버전 인수가 이미 지정되어 있으면 그 값이 우선하므로 선택한 단위와 다른 경우 답변에 알린다.
6. `git log --format=%B <지난 태그>..HEAD`로 커밋 노트를 읽는다(`node scripts/release-notes.mjs`가 종류별로 묶어 보여 준다). 앞머리(`feat:`·`fix:` …)가 없거나 내용을 알 수 없는 커밋 제목이 있으면 그 커밋을 알린다(고치지 않는다).
7. 사용자용 업데이트 내역 초안을 `release-notes.draft.md`에 쓴다. 이 글이 GitHub 릴리스와 Discord 업데이트 알림에 그대로 나간다.
   - `npm run release`를 실행하는 프로젝트 원본 폴더의 루트에 쓴다.
   - 첫 줄은 정확히 `<!-- agenthub-release-draft base=<git rev-parse HEAD 결과> bump=<5단계에서 고른 patch·minor·major 중 하나> -->`로 쓴다. 예: `<!-- agenthub-release-draft base=0123456789abcdef0123456789abcdef01234567 bump=minor -->`. 릴리스할 때 HEAD가 이 커밋과 다르면(그 뒤 커밋이 생기면) 초안의 버전 단위와 노트를 모두 쓰지 않으므로 준비를 다시 한다.
   - 읽는 사람은 앱 사용자다. 무엇을 할 수 있게 됐는지, 무엇이 고쳐졌는지를 쓴다. 파일 이름·함수·API·내부 구조, "MCP"·"worktree" 같은 용어는 쓰지 않거나 풀어 쓴다("세션끼리 메시지를 주고받을 수 있습니다", "세션마다 따로 쓰는 작업 폴더").
   - `### 새 기능`, `### 고친 것`, `### 바뀐 점` 중 해당하는 절만 두고 그 아래에 `- ` 항목을 쓴다. 항목은 한 줄, 큰 것부터. 테스트·문서·스킬 정리처럼 사용자가 느끼지 못하는 변경은 뺀다.
   - 전체 1500자 안. 커밋에 없는 내용을 지어내지 않는다.
   - 초안 전문을 답변에도 붙인다. 사람이 승인하기 전에 파일을 직접 고칠 수 있다.
8. 하지 않는 것: `release-notes.draft.md`와 4단계의 문서 밖의 파일 수정, 4단계 문서 커밋 밖의 `git add`·`git update-index`·`git commit`, 다른 세션이 고치던 줄을 되돌리거나 커밋에 담는 것, `git commit --amend`, `git stash`, `npm run release`, `npm version`, `git push`, `git tag`, `gh release`, Discord로 직접 보내기.
9. 모두 통과했으면 4단계에서 만든 문서 커밋(해시·제목·고친 곳), 지난 릴리스 이후 바뀐 점 요약, 자동 적용할 버전 단위와 선택 이유, 업데이트 내역 초안을 쓰고, **마지막 줄에 정확히 "릴리스 준비"**라고 쓴다.
   - 실패했으면 이 말을 쓰지 않고 초안도 쓰지 않는다. 대신 실패한 단계와 이유를 쓴다.

## 릴리스가 실패해서 돌아왔을 때
- 출력을 보고 원인을 진단해 보고한다. 직접 고치거나 다시 릴리스하지 않는다.
- 빌드 전에 멈췄으면 올린 버전은 임시 작업 트리와 함께 사라진다. 버전 커밋·태그가 만들어졌는데 현재 브랜치로 fast-forward나 push가 안 된 상태인지(`git tag`, `git log`로 확인) 알린다.
- 임시 작업 트리(`agenthub-release-*`)가 `git worktree list`에 남아 있으면 알린다.
